# Token Exchange

## Overview

Medplum supports [OAuth 2.0 Token Exchange](https://datatracker.ietf.org/doc/html/rfc8693). Your application supplies an external user access token, and Medplum validates it with the configured IDP and issues a user-scoped Medplum token. The exchange itself does not redirect the user.

Use the shared setup and request format below, then follow the [client-held](#client-held-medplum-tokens) or [server-held](#server-held-medplum-tokens) implementation steps. Both use the same exchange endpoint. If Medplum should handle the external IDP callback during login, follow the [external IDP authorization-code flow](/docs/auth/external-identity-providers#authorization-code-flow).

## Prerequisites

- Obtain an external **access token** for the user through your application's login flow. An ID token or application session cookie is not a substitute for this input.
- Configure an IDP UserInfo endpoint that accepts that access token.
- Provision the Medplum user, profile, and project membership. A clinical `Patient` or `Practitioner` record alone is not a login; see [User Management](/docs/user-management).
- Choose email matching or external ID matching consistently with your provisioning process. See [Using External IDs](/docs/user-management/external-ids).

## Set up your ClientApplication

In order to authenticate the user, Medplum's authentication server will call the `/userinfo` endpoint of the external identity provider and check for a valid response. Therefore, it is important that the corresponding [`ClientApplication`](https://app.medplum.com/ClientApplication) in your Medplum project has an identity provider set up with a user info URL specified.

To set up an identity provider for your [`ClientApplication`](https://app.medplum.com/ClientApplication):

1. Log in to your Medplum project.
1. Navigate to the [ClientApplications page](https://app.medplum.com/ClientApplication).
1. Click on the [`ClientApplication`](https://app.medplum.com/ClientApplication) that you would like to set up with an identity provider.
1. Click the "Edit" tab.
1. Scroll down to the "Identity Provider" section.
1. Enter the `/userinfo` URL for your external identity provider in the "User Info URL" textbox.
1. Click "Save" to save your changes.

:::caution[Scopes]

By default, Medplum will use the user's email address to identify their Medplum user, so you must make sure that you have requested your external access token with the `email` scope.

If you would like to use the `sub` (subject) identifier assigned by the external authentication provider, you must check "Use Subject" in your "Identity Provider" settings.

:::

## Exchanging tokens

Once you have set up the identity provider for your [`ClientApplication`](https://app.medplum.com/ClientApplication), you can use the `/oauth2/token` endpoint to exchange the external access token for a Medplum access token.

The client makes a token exchange request to the token endpoint with an extension grant type using the HTTP POST method. The following parameters are included in the HTTP request entity-body using the application/x-www-form-urlencoded format with a character encoding of UTF-8.

- **grant_type**: The constant value of "urn:ietf:params:oauth:grant-type:token-exchange".
- **client_id**: The selector for the external auth provider making the exchange request. This is either the ID of the [`ClientApplication`](https://app.medplum.com/ClientApplication) in your Medplum project, or the `clientId` of a server-level [`externalAuthProviders`](#server-scoped-users-and-the-membership_id-parameter-self-hosted-only) entry (self-hosted only).
- **subject_token**: The access token that was generated by the external identity provider.
- **subject_token_type**: The subject token type as defined in Section 3. Only "urn:ietf:params:oauth:token-type:access_token" is currently supported.
- **membership_id** (optional): The [`ProjectMembership`](/docs/api/fhir/medplum/projectmembership) that the resulting Medplum token should be scoped to. Use it to disambiguate when the resolved user has more than one candidate membership. The set of candidates depends on the `client_id`: a `ClientApplication` constrains the candidates to its own project, while a server-level provider considers the user's memberships across all projects — see [Server-scoped users and the `membership_id` parameter](#server-scoped-users-and-the-membership_id-parameter-self-hosted-only) below.

## Client-held Medplum tokens

In this implementation, your browser or native application performs the exchange and calls Medplum directly.

1. Complete the external IDP login and obtain the user's access token.
2. Call `exchangeExternalAccessToken(externalAccessToken, clientId, membershipId)` on the `MedplumClient` used by that user's application session. `clientId` selects the configured provider; `membershipId` is optional, but should be supplied when the user has more than one candidate membership.
3. Await the exchange before making Medplum requests or rendering components that require an authenticated Medplum client. The SDK stores the resulting login state on that client and uses its Medplum token for subsequent requests.
4. Manage the external and Medplum sessions separately. Apply platform-appropriate credential storage and use the [token management](/docs/auth/session-management) and [logout](/docs/auth/logout) documentation for the Medplum session.

Use the SDK example in [Exchanging tokens](#exchanging-tokens). Keep the external token for APIs that accept it; use the resulting Medplum token for Medplum API calls. Do not include an application client secret in browser or native code.

## Server-held Medplum tokens

In this implementation, your backend performs the exchange and makes Medplum requests using the resulting **user-scoped token**. The client continues to authenticate to your backend through your application's existing session mechanism.

1. Authenticate the incoming application request and obtain the external user access token associated with that session. If your application only has a session cookie, retrieve the external access token through your existing IDP integration; do not send the cookie as `subject_token`.
2. Resolve the intended Medplum membership from your trusted identity-to-membership mapping. Check that the requested application context is authorized for that identity.
3. Exchange the external access token using the same endpoint or SDK method as the client-held implementation. Use a `MedplumClient` and credential storage isolated to that user and session context; do not change the active login on a singleton shared across users.
4. Make the user's Medplum requests with that authenticated client. Return the application's response to the caller while retaining the Medplum credentials on the backend. The resolved membership's access policy applies to these requests; an On-Behalf-Of header is not needed.

The existing [Node.js token exchange example](https://github.com/medplum/medplum/tree/main/examples/medplum-token-exchange-demo) demonstrates the exchange call, with hosted `ClientApplication` configuration and self-hosted provider configuration documented in its README. It is a command-line example, not a complete session store or application proxy.

### Backend session handling

When incorporating the exchange into a running application:

- **Token reuse:** If you cache credentials, bind entries to the authenticated identity, provider/client, membership, and application session. Reject inconsistent mappings and isolate any cached FHIR responses as well as tokens.
- **Expiry and renewal:** Handle expiration and failed renewal explicitly. If no usable Medplum credential remains, obtain a valid external user token and exchange again, or require login. Never substitute an application token when a user-token request fails.
- **Logout:** Revoke the relevant Medplum session using the [logout instructions](/docs/auth/logout), remove cached credentials, and end the application session according to your policy. External IDP logout is a separate integration concern.
- **Live updates:** If the client never receives Medplum credentials, implement an authenticated backend-to-client delivery path. A server-held token does not give the browser a directly authenticated Medplum connection.

**Server-held tokens and server-scoped users are different concepts.** Keeping the token on your backend works with a project-scoped user and a hosted `ClientApplication`. The configuration below concerns which memberships a provider can resolve, not where your application stores the token.

## Server-scoped users and the `membership_id` parameter (self hosted only)

The setup above configures the external identity provider on a single [`ClientApplication`](https://app.medplum.com/ClientApplication). Because a `ClientApplication` lives inside one [`Project`](/docs/api/fhir/medplum/project), the exchange is implicitly scoped to that project: Medplum only considers the user's [`ProjectMembership`](/docs/api/fhir/medplum/projectmembership) records **within the client's project**. For most [project-scoped users](/docs/user-management/project-vs-server-scoped-users) that resolves to a single membership and the token "just works".

In two situations there is more than one candidate membership, and you need `membership_id` to pick deterministically:

- **Multiple memberships in the same project.** If the resolved user has more than one membership in the client's project, the exchange would otherwise fall back to the _first_ one. Pass `membership_id` to choose. This works with a plain `ClientApplication` — no server-level config required.
- **Reaching a different project (server-scoped users).** [Server-scoped users](/docs/user-management/project-vs-server-scoped-users#server-scoped-users) (typically developers and administrators) can have a membership in _many_ projects. A `ClientApplication` cannot reach across projects — it only ever resolves into its own project — so to target an arbitrary project you must use a **server-level external auth provider** (below), where `membership_id` both selects the membership and derives the project.

### Configure a server-level external auth provider

To support token exchange for server-scoped users, configure the identity provider at the server level via [`externalAuthProviders`](/docs/self-hosting/server-config) instead of (or in addition to) a per-`ClientApplication` identity provider. Unlike a `ClientApplication`, a server-level provider is not tied to any single project, so the exchange can resolve into whichever project you target.

:::caution[Self-hosted only]

`externalAuthProviders` is part of the [server config](/docs/self-hosting/server-config) and requires super admin access, so it is only available on self-hosted deployments. On Medplum's hosted service, token exchange is scoped to a `ClientApplication`'s project. If you need cross-project token exchange on hosted Medplum, contact [Medplum support](/contact).

:::

```json
{
  "externalAuthProviders": [
    {
      "issuer": "https://your-idp.example.com",
      "clientId": "your-token-exchange-selector",
      "userInfoUrl": "https://your-idp.example.com/oauth2/userinfo"
    }
  ]
}
```

The `clientId` you assign here is the value you pass as `client_id` in the exchange request. (If you omit the top-level `clientId`, the server falls back to `identityProvider.clientId`.) Restart the server after updating the config.

### Why you must pass `membership_id`

When you call the token endpoint with a server-level provider, Medplum validates the external token and resolves the user by email or `sub`. If you **do not** pass `membership_id`, the server falls back to the user's _first_ membership — which is non-deterministic for a server-scoped user that belongs to several projects, and may not be the project you intended.

To pick the project explicitly, include `membership_id` in the request. The server reads that [`ProjectMembership`](/docs/api/fhir/medplum/projectmembership), derives the project from it, and issues a token scoped to that membership:

```bash
curl -X POST 'https://your-medplum-server.example.com/oauth2/token' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
--data-urlencode "subject_token_type=urn:ietf:params:oauth:token-type:access_token" \
--data-urlencode "client_id=your-token-exchange-selector" \
--data-urlencode "subject_token=<External Access Token>" \
--data-urlencode "membership_id=<ProjectMembership id>"
```

With the SDK, pass it as the third argument to [`exchangeExternalAccessToken()`](/docs/sdk/core.medplumclient.exchangeexternalaccesstoken):

```ts
await medplum.exchangeExternalAccessToken(externalAccessToken, clientId, membershipId);
```

### You own the identity-to-membership mapping

The external IdP token only carries the external identity (email or `sub`). It has no knowledge of Medplum projects or `ProjectMembership` ids. That means **your application is responsible for knowing which membership to target** for a given user and context, and for passing the right `membership_id` on each exchange:

- **Keep track of memberships in your own system.** Persist the mapping from your external user (and the project/tenant context they're acting in) to the corresponding Medplum `ProjectMembership` id, so you can look it up at exchange time.
- **Discover memberships when you need to.** You can enumerate a user's memberships by searching [`ProjectMembership`](/docs/api/fhir/medplum/projectmembership) resources (for example, by `profile` or `user`) with a sufficiently privileged token, then store the ids you care about.
- **Validate the target.** An invalid or unreadable `membership_id` is rejected with an `invalid_request` error, so confirm the membership exists and belongs to the expected user/project before relying on it.

:::tip[Example]

The [Node.js token exchange example](https://github.com/medplum/medplum/tree/main/examples/medplum-token-exchange-demo) includes self-hosted provider configuration and an optional `membership_id`. Its hosted configuration remains limited to the `ClientApplication`'s project.

:::

## Legacy `/auth/exchange` endpoint

Before supporting the OAuth 2.0 Token Exchange standard, Medplum provided the `/auth/exchange` endpoint. This endpoint is deprecated, and developers are encouraged to adopt the standard.
