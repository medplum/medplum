**If you will be at HLTH in November, email us at [hello@medplum.com](mailto:hello@medplum.com)** and we will find time to connect with the Medplum team.

**Medplum v5 earned [Drummond Validated FHIRplace Silver status for Coverage Requirements Discovery](/blog/fhirplace-silver-crd-2026) in both the provider and payer roles**, determined October 1. It is the first external validation of the prior authorization work that has been running all year, and it comes with a new [CMS-0057-F](/docs/compliance/cms-0057-f) page laying out which payers the rule touches and when.

October brought 296 commits from 20 contributors, with thirteen patch releases, v5.2.1 through v5.2.13.

[Scheduling](/blog/2026-roadmap#scheduling) grew a configuration workspace a practice admin can actually run its calendar from, recurring appointment series through [`$book`](/docs/scheduling/appointment-book) and [`$hold`](/docs/scheduling/appointment-hold), and blocked time. The [Provider App](/blog/2026-roadmap#provider-application) gained draft lab orders and a claim submission path with its own [guide](/docs/provider/submitting-claims). A `Project` can now be deactivated, archived, and restored.

All of this continues to drive forward our [2026 roadmap priorities](/blog/2026-roadmap).

## Features

### Scheduling

<img src="https://github.com/Filupnot.png" alt="Philip Knott" width="50" height="50" style={{borderRadius: '50%'}} /> **[Philip Knott](https://github.com/Filupnot)**, <img src="https://github.com/noahsilas.png" alt="Noah Silas" width="50" height="50" style={{borderRadius: '50%'}} /> **[Noah Silas](https://github.com/noahsilas)**, and <img src="https://github.com/kevinwadeshaw.png" alt="Kevin Shaw" width="50" height="50" style={{borderRadius: '50%'}} /> **[Kevin Shaw](https://github.com/kevinwadeshaw)**

[Scheduling](/blog/2026-roadmap#scheduling) was the largest area of the month again. September built the operations; October built the two screens a practice lives in — the workspace the front desk books from, and the configuration workspace the practice admin sets it all up in.

<img src="/img/blog/2026-10-scheduling-recurring-marks.png" alt="Scheduling workspace showing a week of appointments as tinted blocks, blocked time on one calendar, a recurring series marker, and an appointment details popover" style={{maxHeight: '400px', maxWidth: '100%'}} />

- **A configuration workspace** — The [`SchedulingConfigWorkspace`](https://storybook.medplum.com/?path=/story/medplum-schedulingconfigworkspace--basic) introduced in September now lists providers, rooms, and devices beside visit types, each section read independently so one failure does not blank the page. Picking an actor opens its page ([Storybook](https://storybook.medplum.com/?path=/story/medplum-schedulingconfigworkspace-actorpage--provider-service-facilities)): name, status, the visit types its calendar offers with the duration and hours in effect, its NPIs, its time zone, and the service facilities it works at. Rooms and devices can be created from the sidebar and renamed in place. Providers can be created without an NPI, since a room scheduler and a billing provider are not the same list, and providers the workspace did not create keep their status locked so an admin cannot deactivate a `Practitioner` the rest of the system depends on. A provider's `PractitionerRole` writes are worked out from the service facilities chosen rather than hand-edited

<img src="/img/blog/2026-10-scheduling-config-actors.png" alt="Scheduling configuration workspace listing visit types, providers, devices, and rooms, with a provider's page showing the visit types they offer" style={{maxHeight: '400px', maxWidth: '100%'}} />

- **Offering visit types, from either side** — A [visit type's page](https://storybook.medplum.com/?path=/story/medplum-schedulingconfigworkspace-visittypepage--existing) shows which providers, rooms, and devices offer it; an actor's page shows [every visit type available to offer](https://storybook.medplum.com/?path=/story/medplum-schedulingconfigworkspace-actorpage--provider-offering-all-visit-types), filtered and paged so a system with hundreds of visit types does not try to render them at once. Offering and un-offering works from either direction, and un-offering says plainly that existing appointments are not changed
- **Booking requirements on a visit type** — The `requires-prior-auth` behavior from September is now editable: a visit type's page sets whether booking it requires procedure codes, diagnosis codes, or a medical-necessity confirmation, and which service facilities offer it ([Storybook](https://storybook.medplum.com/?path=/story/medplum-schedulingconfigworkspace-visittypepage--prior-authorization))

<img src="/img/blog/2026-10-scheduling-booking-requirements.png" alt="Visit type page with service facilities and checkboxes for requiring procedure codes, diagnosis codes, and medical necessity confirmation" style={{maxHeight: '400px', maxWidth: '100%'}} />

- **Recurring series** — [`$book`](/docs/scheduling/appointment-book) and [`$hold`](/docs/scheduling/appointment-hold) expand a weekly `recurrenceTemplate` returned by [`$find`](/docs/scheduling/appointment-find) into every occurrence of the series and book or hold them in one transaction, all or none, each occurrence sharing one series identifier and carrying its R5 `recurrenceId`. The booking form offers a **Repeat** field of two to six weekly occurrences; the times offered are each a series' first occurrence, and booking one books them all. When [`$reschedule`](/docs/scheduling/appointment-reschedule) moves a single occurrence off the pattern it is marked with R5's `occurrenceChanged` as an R4 cross-version extension, and a manual reschedule marks it the same way, so the marker reflects whether the occurrence left the pattern rather than which code path moved it. Recurring appointments are [marked on the calendar](https://storybook.medplum.com/?path=/story/medplum-schedulingworkspace-appointmentdetails--recurring)
- **Blocked time** — Time can be taken off one or more calendars without booking a visit into it. A block form asks for a start and end, the providers, rooms, and devices to block, and an optional comment, and writes a `busy` `Slot` over the time on each. Clicking a blocked `Slot` opens its details beside the calendar, and a management view lists and edits existing blocks. Slots attached to an appointment are not editable this way
- **A calendar you can read at a glance** — Appointments draw as tinted blocks with a color bar, `Slot`s render as gray foreground events rather than per-schedule colors, free slots are hidden, today's date is circled, the now line and calendar headers were restyled, the selected event is highlighted, and each appointment appears exactly once no matter how many of its actors' calendars are shown. A service type can set its own [scheduling color](https://storybook.medplum.com/?path=/story/medplum-multicalendar--theme-colors)
- **Getting around** — A [collapsible Calendars sidebar](https://storybook.medplum.com/?path=/story/medplum-schedulingworkspace-calendarspanel--with-filters), a month/year picker, a **Today** button separated from the previous and next arrows, a time finder that slides in and out with the day selection widget inside it, calendar filters by site and visit type, pill tabs on a shared pane header, and workspace controls moved into the calendar toolbar
- **Appointment details** — The [details pane](https://storybook.medplum.com/?path=/story/medplum-schedulingworkspace-appointmentdetails--basic) shows the MRN, the primary provider, the service facility, and the visit type; a pending appointment can be confirmed from it; procedure and diagnosis codes and medical necessity can be edited there; an appointment can be [linked to an external system](https://storybook.medplum.com/?path=/story/medplum-schedulingworkspace-appointmentdetails--external-link); and notes are written when an appointment is booked or edited. Appointments become [read-only twelve hours after they end](https://storybook.medplum.com/?path=/story/medplum-schedulingworkspace-appointmentdetails--past-edit-window)
- **Booking that matches how a front desk works** — A provider is no longer required in [find-and-book](https://storybook.medplum.com/?path=/story/medplum-appointmentactorselect--room-at-a-clinic), since a room or a device is sometimes the scarce resource. The visit being booked is drawn as a draft on the calendar, booking answers are kept as the user moves across days, a newly booked appointment is selected and brought on screen, and typing a time books it on one provider per row rather than every alternative. The booking form and its times scroll separately
- **Naming** — `location` became **service facility** throughout, with a shared input that lists sites by name, and inactive service facilities are left out of the booking pickers

### Provider App

<img src="https://github.com/techdavidy.png" alt="David Yanez" width="50" height="50" style={{borderRadius: '50%'}} /> **[David Yanez](https://github.com/techdavidy)**, <img src="https://github.com/maddyli.png" alt="Maddy Li" width="50" height="50" style={{borderRadius: '50%'}} /> **[Maddy Li](https://github.com/maddyli)**, and <img src="https://github.com/finnbergquist.png" alt="Finn Bergquist" width="50" height="50" style={{borderRadius: '50%'}} /> **[Finn Bergquist](https://github.com/finnbergquist)**

- **Lab orders as drafts** — An order can be saved as a draft and submitted later, supporting situations where a provider builds the order during the visit and sends it once the specimen is collected. A new `LabOrdersPanel` React component ([Storybook](https://storybook.medplum.com/?path=/story/medplum-laborderspanel--completed)) lists completed, open, and revoked orders beside the selected report's results, and `Observation` values keep their original decimal precision where it was preserved on the way in

<img src="/img/blog/2026-10-provider-lab-orders-panel.png" alt="LabOrdersPanel showing completed, open, and revoked lab orders beside a diagnostic report with reference ranges and interpretations" style={{maxHeight: '400px', maxWidth: '100%'}} />

- **Claims** — Claims can be submitted from a visit's details and billing tab, with a [walkthrough guide](/docs/provider/submitting-claims) and a [video](https://youtu.be/nG03K6Ps_mE) covering the flow end to end. The service facility is included on submission, the app checks whether the claim custom operations exist before offering the action rather than failing at submit time, and the get-started flow registers a charge item modifiers `ValueSet`
- **Eligibility** — X12 service types can be selected when running an [eligibility check](/docs/billing/insurance-eligibility-checks), so a check can ask about the benefit category the visit actually falls under instead of general coverage
- **[Spaces](/docs/provider/spaces)** — The conversation pane was extracted from the Spaces inbox and the inbox moved onto the shared [list-with-detail layout](https://storybook.medplum.com/?path=/story/medplum-listwithdetailpane--basic), so Spaces matches the rest of the app, with a hook for embedding it elsewhere

- **Imported records land on the right patient** — Importing a [SMART Health Link](/docs/intake/smart-health-links) rewrites every `Patient` reference in the bundle to the target patient rather than only the first entry, and scopes identifier-based conditional creates to that patient. A bundle can carry one `Patient` per source system, and the unmatched references were previously saved dangling
- **Search** — Filter UX improvements in [`SearchControl`](https://storybook.medplum.com/?path=/story/medplum-searchcontrol--all-buttons), and the menu button is hidden when there is nothing in it

### Platform and API

<img src="https://github.com/codyebberson.png" alt="Cody Ebberson" width="50" height="50" style={{borderRadius: '50%'}} /> **[Cody Ebberson](https://github.com/codyebberson)**, <img src="https://github.com/mattwiller.png" alt="Matt Willer" width="50" height="50" style={{borderRadius: '50%'}} /> **[Matt Willer](https://github.com/mattwiller)**, and <img src="https://github.com/mattlong.png" alt="Matt Long" width="50" height="50" style={{borderRadius: '50%'}} /> **[Matt Long](https://github.com/mattlong)**

- **Project lifecycle** — A `Project.active` flag deactivates a project without deleting it: logins, client credentials, refresh, existing access tokens, basic auth, and external IdP tokens are all rejected, the project is hidden from the picker, subscriptions stop queueing and queued jobs are dropped, and cron bots skip their runs but stay registered so they resume on reactivation. Only super admins can change it, so a project admin cannot lock themselves out. Alongside it, `Project/$archive` exports every version of every resource in a project, tombstones included, as per-type NDJSON with ids and `meta` intact, and `$restore` loads that archive into another Medplum server — the path for moving a project between a hosted and a self-hosted deployment, or handing a customer their data. Both are gated behind a project feature, run on the bulk export queue, and apply the caller's access policy to every version. The `medplum` CLI has `project archive` and `project restore` commands, and expunging a project now expunges its deleted resources too ([Maddy Li](https://github.com/maddyli), [Cody Ebberson](https://github.com/codyebberson))
- **Bulk export** — Exports are queued through restartable BullMQ processing, so a server restart mid-export resumes instead of stranding the job. `_typeFilter` is supported for System and Patient export per the Bulk Data IG: each value is parsed and validated before the job starts, so an invalid filter returns a 400 rather than a job that fails later; filters constrain only their named type; and multiple filters on one type are ORed with de-duplication enabled only where it is needed. Group export paginates by resource type and searches large groups in member chunks, `OperationDefinition` is excluded, parameters are read from POST bodies and repeated query values, and polling a failed export returns a 400 `OperationOutcome` instead of a success shape. See [bulk FHIR](/docs/api/fhir/operations/bulk-fhir)
- **`If-Match` on delete** — A FHIR delete honors `If-Match`, so a client can refuse to delete a resource that changed since it read it
- **Bots** — `Bot.rawBody` is honored on `$execute` and custom operations, not only public webhooks ([Finn Bergquist](https://github.com/finnbergquist)); bot input storage has lifecycle management; running a bot that was never deployed returns a clear error; cron schedules are reloaded in the post-deploy migration; streaming bot responses protect their headers; and bot execution access tokens are cached
- **Search and terminology** — Spec-compliant date range search and `$validate` input handling, a configuration option to restrict chained search, `ValueSet/$expand` searches `compose.include.concept.code`, and single-resource lookups that match more than one resource are logged
- **The `medplum` CLI** — `medplum generate-types` generates TypeScript interfaces from FHIR profiles, moved out of the internal generator package and into `@medplum/core` so it is available to anyone with profiles of their own. The CLI also sends a user agent string, and no longer resumes an expired session during login ([Ian Plunkett](https://github.com/ianplunkett))
- **API description** — Conditional interactions and OAuth2 are documented in the OpenAPI spec, which is linked from an [RFC 9727](https://www.rfc-editor.org/rfc/rfc9727.html) API catalog, and `llms.txt` was added to www.medplum.com so coding assistants can find the docs
- **Smaller changes** — FHIR ranges are enforced for `integer`, `positiveInt`, and `unsignedInt` ([Karl Pietrzak](https://github.com/The-Alchemist)), requests sent with an already-aborted signal are not cached ([Philip Knott](https://github.com/Filupnot)), batch creates honor server-assigned ids only where the spec allows, a missing operation body reads as no parameters, project SMTP transport setup was tightened ([Darren Eam](https://github.com/deam65)), the project list in the account menu scrolls ([Karl Pietrzak](https://github.com/The-Alchemist)), radio and checkbox questions are marked unavailable when their value set is missing ([Philip Knott](https://github.com/Filupnot)), and C-CDA date and time precision is preserved through the FHIR mappings

### Enterprise: Scale, Database, and Self-Hosting

<img src="https://github.com/mattlong.png" alt="Matt Long" width="50" height="50" style={{borderRadius: '50%'}} /> **[Matt Long](https://github.com/mattlong)**, <img src="https://github.com/mattwiller.png" alt="Matt Willer" width="50" height="50" style={{borderRadius: '50%'}} /> **[Matt Willer](https://github.com/mattwiller)**, and <img src="https://github.com/ThatOneBro.png" alt="Derrick Farris" width="50" height="50" style={{borderRadius: '50%'}} /> **[Derrick Farris](https://github.com/ThatOneBro)**

[Enterprise scale](/blog/2026-roadmap#enterprise-scale--infrastructure) work continued toward sharding and spent the rest of the month on query cost:

- **Sharding** — Shard configuration and sharded test infrastructure landed, super admin endpoints use a shard-aware database pool, resource cache entries are scoped to the shard they were written from, and background job preparation passes a job data context carrying the shard id. Production behavior is unchanged
- **Reader routing** — `readonlyBatchOnReader` and `chainedSearchOnReader` project settings send read-only batches and chained searches to a reader instance, and resources read from a reader are no longer written into the cache, where replication lag could otherwise make a stale read sticky
- **Indexes and query cost** — A partial filter index on `Encounter`, an experimental partial index on `Task`, reference lookup table rows diffed on write rather than rewritten, an optimized `Repository.searchResources`, a first round of optimization on the dispatch job, and delete background jobs deferred until the transaction commits
- **Static hosting** — foomedical.com and provider.medplum.com are served from S3 and CloudFront, with preview deployments on pull requests, and the CDK can pin additional container images to digests at synth time. Blocked email domains are configurable through CDK
- **Operations** — Centralized background job membership checks, circular reference errors avoided in JSON serialization, dollar signs kept out of log lines, Node bumped in the server image, and Docker Hub pulls authenticated for CI service containers

## Compliance

<img src="https://github.com/codyebberson.png" alt="Cody Ebberson" width="50" height="50" style={{borderRadius: '50%'}} /> **[Cody Ebberson](https://github.com/codyebberson)**, <img src="https://github.com/mattwiller.png" alt="Matt Willer" width="50" height="50" style={{borderRadius: '50%'}} /> **[Matt Willer](https://github.com/mattwiller)**, and <img src="https://github.com/ThatOneBro.png" alt="Derrick Farris" width="50" height="50" style={{borderRadius: '50%'}} /> **[Derrick Farris](https://github.com/ThatOneBro)**

[Compliance](/blog/2026-roadmap#compliance-h1-2026) had its biggest month of the year:

- **[FHIRplace Silver for CRD](/blog/fhirplace-silver-crd-2026)** — Medplum v5 is Drummond Validated for Coverage Requirements Discovery in both the provider and payer roles, determined October 1 in the Q3 2026 testing cycle. Validation means confirmed interoperability with multiple partners in a production-representative environment, not a self-attestation
- **[CMS-0057-F](/docs/compliance/cms-0057-f)** — A new page on the CMS Interoperability and Prior Authorization Final Rule: which payers it applies to, what is required when, where the Da Vinci guides are recommended rather than required, and what Medplum provides. It is deliberately kept separate from [HTI-4](/docs/compliance/hti-4), which is ONC health IT certification and a different program
- **[`Patient/$match`](/docs/api/fhir/operations/patient-match)** — Updated to the CMS patient match specification v3.4.0
- **Identity and sessions** — Refresh tokens are single-use and revoke the chain on reuse, authorization codes expire after ten minutes, setting a password revokes every outstanding login, outstanding password links are retired on a password change or rescope, a rescope to server is rejected when the email is already in use, first-login MFA enrollment honors the project's `allowedMfaMethods`, admin MFA and password reset are limited to project-scoped users, and `/auth/me` lists only granted logins as sessions
- **OAuth2 and clients** — The client redirect URI is confirmed before the sign-in form is shown, `ClientApplication.launchUri` schemes are validated, [SMART scopes](/docs/access/smart-scopes) are applied to project admin rules, each subscriber's token scopes are applied to WebSocket subscription notifications, and on-behalf-of targets must be an active membership
- **Project isolation** — Presigned storage URLs validate their request path and project, attachment `Binary`s in [`$expunge`](/docs/api/fhir/operations/expunge) are limited to the resource's project, DICOM raw files are read with a project-scoped repository, bots are resolved with a project access check and super admin bot creation is scoped to the target project, file system storage paths stay within the base directory, the CORS origin is compared exactly against the app base URL origin, a malformed `AccessPolicy` criteria fails closed, literal values are escaped in identity lookups, and `$deploy` has an explicit permission check
- **Account self-service** — Self-service account routes require an unscoped login and tightened input validation, the email API is limited to the documented options, project registration is controlled by a new server config, and blocked email domains are configurable
- **Observability for the above** — Caller identity on authentication errors, SMART scopes with partial permissions, Google sign-ins whose client ID matches multiple projects, login redirect URIs not registered for the client, unverified email claims from external identity providers, identity provider details on external auth callbacks, and access policy field matches on create are all logged, so the next review has evidence rather than inference
- **Code of Conduct** — A [Code of Conduct](/docs/contributing/code-of-conduct) was added to the contributing docs ([Tim Ray](https://github.com/timray721))
